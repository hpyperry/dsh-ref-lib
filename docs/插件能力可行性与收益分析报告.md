## 1. DSH 核心技术底座分析

### 1.1 整体架构：一切皆插件的 Cordis 生态

DSH 是 DeepSeek AI 开源的 agent harness（智能体框架），当前处于**开发者预览**阶段（`0.1.1-rc.2`，破坏性兼容变更未冻结）。其架构基石是 vendor 引入的 **Cordis 插件框架**（设计源自论文《A Programming Paradigm for Spatiotemporal Composability》），核心主张是：

> **产品的每一部分都是插件**，包括模型适配器、工具注册表、会话日志、agent loop 本身，每一部分都可以从配置替换。

Cordis 的五个核心概念直接定义了 DSH 的扩展范式：

1. **插件即 Service 对象**——可以是带 `inject`/`apply(ctx)` 的函数，也可以是 `Service` 子类，生命周期由 Cordis 挂载到上下文中；
2. **上下文是服务的容器**——每个服务占据稳定的 `ctx.<key>`（如 `ctx.tools`、`ctx.llm`、`ctx.sessions`），插件之间通过 key 查找服务，**而非 import 具体实现**（依赖倒置）；
3. **`inject` 声明服务依赖**——插件声明所需服务后等待其就绪才启动，加载顺序由服务依赖表达，而非手工编排；
4. **类型化事件通信**——服务通过 TypeScript 声明合并注册事件名，以 `emit`（观察）、`waterfall`（环绕中间件）、`parallel`（并行扇出）、`serial`（按序）四种分发模式通信；
5. **注册是可逆副作用**——提示词片段、工具 schema、适配器、提供方、监听器经 `ctx.effect()` / `ctx.on()` 安装，reload 与 teardown 时自动撤销。

**没有需要打补丁的特权内核**：扩展 dsh 的方式就是把插件挂载到其他插件旁边；所有注册都是副作用，插件卸载即撤销。这一性质决定了任何第三方插件（含 ref-lib）只要遵守 seam 契约，就能与官方插件平级共存、互相 patch。

### 1.2 全插件化设计原理与分层装配机制

运行中的 `dsh` 是一棵**插件树**，由启动时按序叠加的各层组合而成：

- **profile（装配档）**：存放在 Harness home 的具名组装，列出叠放的组合包、存放树外插件、保存用户 `cordis.patch.yml`；`web` 与 `headless` 作为模板随发行版交付；
- **组合包（bundle）**：Cordis 配置项 + 挂载代码的分发格式，其插入内容始终可被其上各层 patch；
- **层序**：`dsh-base`（模型适配器、工具、持久化、沙箱与审批策略、设置、凭据、遥测）→ `dsh-web-app`（浏览器应用）/ `dsh-headless`（一次性运行器）→ profile 的 `cordis.patch.yml` → home 级 patch → `--patch` overlay；
- **patch 语义**：按 id 定位条目并替换整个 config，或插入新条目（`- insert: - id: ref-lib, name: '@hpyperry/dsh-ref-lib'` 即 ref-lib 的装配方式）。

核心主干包及职责（`ctx` 键）：

| 包 | 职责 | ctx 键 |
|---|---|---|
| core/session | 仅追加的 `SessionEvent` 日志与内存存储（唯一真源） | `ctx.sessions` |
| core/system-prompt | 提示词片段与工具 schema 的组装 | `ctx.systemPrompt` |
| core/tools | 作用域化的工具注册表 + 带把关的执行流水线 | `ctx.tools` |
| core/agent | `Agent` 接口、活跃 agent 注册表、`agent/*` 事件 | `ctx.agents` |
| core/agent-loop | 默认驱动器（唯一公开 `Agent` 约定的实现） | `ctx.agentLoop` |
| core/scope | 按 agent 划分作用域的注册原语 | 库，无 ctx 键 |
| llm/llm | 消息/流式词汇表 + 适配器 seam | `ctx.llm` |

**能力 seam（capability seam）** 是框架可替换能力的统一结构：Service Definition（声明接口）+ Service Provider（实现）+ Consumer（通常是面向模型的工具）。替换一个提供方即可改变整个产品——例如把文件系统与进程提供方指向远程沙箱，Bash/PTY/LSP 一并迁移，无需提供方专属 fork；subagent 提供方在同一接口后从「新建子 agent」到「把轮次委派给另一个产品（Codex / Claude Code）」皆可。

### 1.3 轮次流程与工具调用流水线

一个**步骤**是一次模型请求 + 它调用的工具；一个**轮次**包含零或多个步骤。轮次流程（持久会话事件与实时扩展点混合）：

```
turn/start
  → claim 输入 + 组装提示词段落与工具 schema
  → agent/pre-step（waterfall：改写已领取消息或 reject）
    → step/start → user/message（记录进入步骤的批次）
    → 从日志派生模型历史
    → agent/request → llm/stream → assistant/chunk* → assistant/message
    → tool/call* → tools/pre-execute → 单调守卫 → tools/execute
      → 工具体 → fs 写意图门 → tools/post-execute → finalizeContent → tools/result
    → step/end（工具仍欠请求或有新输入则进入下一步）
  → agent/turn-stopping（serial）
turn/end
```

**工具执行流水线**（`ctx.tools`）是 DSH 对插件能力的核心把关机制，顺序为：

1. `tools/pre-execute` waterfall：钩子、权限策略、沙箱（可改写一次调用，allow / deny / ask）；
2. **单调守卫**：已注册的策略守卫 deny 或 abstain（身份受保护，不得重排——所有者策略仍以守卫注册）；
3. `ctx.approval` 一次性审批（缺席或不可应答则 deny）；
4. `tools/execute` waterfall：超时、重试、指标等环绕分派关注点；
5. 注册的工具 `execute()` 函数体 → `fs/write-intent` / `fs/edit-intent` 门（仅 tool-fs 变更）；
6. 工具自有会话事件（`todo/write`、`fs/observed`、`hook/invoked`、`tool/code-dispatch`）；
7. `tools/post-execute` waterfall：accept / block / replace / 附加上下文；
8. 注册表外层归一化（快照失败 → `isError`）→ `ToolDefinition.finalizeContent`（最后的内容不变式）→ `tools/result`（冻结的权威结果）；
9. 活跃批次的 `additionalContexts` FIFO 注入 → 持久 `tool/result` 事件 → UI 完成卡片。

关键设计点：`schemas()` 通过显式白名单构建面向模型的 `ToolSchema[]`，`execute`/`finalizeContent`/`timeoutMs`/`isConcurrencySafe`/`presentCall`/`presentResult` 等**绝不泄漏到模型请求**；`ToolRestriction`（allow/deny）提供按作用域的工具可见性过滤，委派子 agent 时保留其回报所需工具。

### 1.4 会话日志与「模型可见即已记录」不变式

- 会话日志是**仅追加的 `SessionEvent` 日志**，是完整交互历史的唯一真源；模型消息历史经 `deriveMessages()` 派生，回放即重新派生；
- 事件类型经 `SessionEventMap` 声明合并可扩展，但**持久化加载器只认仓库内生成的白名单 `KNOWN_SESSION_EVENT_TYPES`**；白名单外事件必须带 `ignorable: true` 信封标记才允许跳过，而 `session.append()` 不提供写入该标记的途径；
- 不变式：**模型可见即已记录**——抵达模型请求的一切都必须能从日志重建，新增模型可见输入即需新增会话事件。

该白名单机制是本报告第 4 章 ref-lib v3 事故根因分析的技术背景，也是插件「per-session 状态存储位置」决策的分水岭。

### 1.5 多场景运行模式（Agent Preset）

DSH 以 **agent preset（预设）** 定义「一个会话的 Agent 所运行的插件组装——它的工具、提示词与能力」。随发行版交付四种内置模式（`apps/cli/config/agent-presets/*/preset.yml`）：

| 模式 | 名称 | 能力边界 |
|---|---|---|
| 标准模式 | 功能完整的编码 Agent | 文件编辑、Shell、文件与网页检索、Skills、计划、目标、子代理和工作流 |
| PTC 模式 | 具备标准模式的全部能力 | 通过 Code Mode SDK 呈现工具，让模型用一个 TypeScript 程序组合多步操作（`presetCodeName: 'PTC mode'`） |
| 极简模式 | 仅提供持久 `bash` 与 `str_replace_editor` 的双工具编码 Agent | 其余提示词段落与面向模型的插件一律不进入该 agent |
| 创造模式 | 用于创建自定义 Agent preset | 具备标准模式全部能力 + 运行时检查、插件实验与 preset 创作指导 |

Preset 是可复制、可「设为默认」、可查看的组合快照；`agent-presets` settings namespace 记录当前选择。**预设即作用域边界**——某会话的 Agent 运行哪套插件组装由预设决定，这为插件「按模式差异化生效」提供了原生挂点（第 4 章优化方向）。

### 1.6 子 Agent 调度与联动调用逻辑

`ctx.subagents`（SubagentRuntime）是**具名提供方注册表**（区别于单服务的 bash 执行器），同一上下文可共存多个提供方：

- **一次性（one-shot）提供方**：`spawn-in-process`、`fork`、`acp`、`codex`、`claude-code`、`dsh-sdk`；启动时能力旗标（`outputSchema` / `depthLimit` / `toolFilter` / `persona`）由服务在 `start` 前校验，不支持即**明确拒绝**（fail loud，绝不接受后静默忽略）；
- **可继续（continuable）子 agent**：持久化子 agent 会话 + 至多一个进程内 **Activation**；Agent inbox 是唯一轮次 FIFO；`startContinuable` 预留稳定子 agent id、快照描述符、经 activation-owner 作用域创建子 Agent；`followup` 按 Activation 状态（running 入队 / waiting 唤醒 / 无 Activation 冷恢复）路由；`interrupt` 是唯一公开停止操作；
- **控制工具**：`dsh-tool-subagent`（按提供方委派）、`dsh-tool-subagent-control`（全局 `send_message` / `interrupt_agent` / `list_agents`）、`dsh-tool-subagent-report`（child 作用域 `report` 返回通道）；child 上报经 `reportFrom` 静默投递或 next-step 投递；
- **持久化枚举**：`listChildren` / `listDescendants` 从会话存储 + 可选持久化的实时优先合并中枚举，冷 child 经 projection 折叠恢复身份——不加载、不恢复 Agent；
- **委派深度**：持久 `SessionHeader.delegationDepth` + 可合并扩展 `AgentOptions.subagentDepth`；fork 种子注入使用平衡的已完成轮次前缀（`CreateAgentOptions.seed`）。

工作流（workflow）与目标（goal）是两个同会话编排层：`ctx.workflowEngine` 支持脚本化多 agent 扇出；`ctx.goals` 管理同会话长期目标并经 `agent/*` 续跑。二者与 subagent seam 相互独立、可叠加。

## 2. 插件与 DSH 框架适配匹配度评估

### 2.1 项目业务目标与落地场景

ref-lib 的核心业务目的是：**给任意会话挂上只读参考库，agent 需要查证时先在参考库里检索——而不是凭空猜测或直接搜网**。落地场景包括：团队内部文档/API 规范查证、项目代码库事实核对、多项目知识复用、跨会话知识搬运（fork 继承 + 跨会话导入）、只读审计合规场景。

既定落地方案（AGENTS.md §1）明确的产品边界：

- per-session 隔离 + sidecar 持久化（重启/恢复仍在）；
- 上下文注入采用**定稿英文强制规则**（MUST/ALWAYS 语义 + routing metadata + 权威性/冲突处理 + 外部来源自报 + 只读约束）；
- 数据通道走 `ctx.webServer` 自注册 HTTP 路由（静默、无命令卡片、loopback 护栏）；
- fork 分支会话自动继承（快照语义、条目 id 独立）；跨会话导入（快照副本、不回流）；
- 失效检测（每次读取实时探测、失效不注入、红色提示）；
- 分层只读保证（L1 沙箱强制 / L2 上下文软约束）；
- L0–L4 分层测试标准（2026-08-17 事故后确立）。

### 2.2 适配优势（高度契合点）

**A1. 插件形态完全符合 Cordis 规范。** `RefLibPlugin extends Service`、default export、`ctx.inject(['webServer','sessions'])` / `inject(['commands'])` / `inject(['systemPrompt'])` 声明式依赖——正是官方「第一个插件」教程与 Cordis 五核心概念的标准形态；无特权 API、无对 agent-loop 的侵入。

**A2. 所有能力都落在官方扩展点映射上。** 对照架构文档「新行为的归属位置」表：用户命令 → `ctx.commands` ✓；模型可见上下文 → `ctx.systemPrompt.context` ✓；浏览器数据通道 → `ctx.webServer` ✓；会话间查询 → `ctx.sessionQuery` ✓；fork → `ctx.sessions.fork` / `session/created` ✓。**没有一处使用私有 hack 或对内核的 patch**。

**A3. 数据模型尊重「模型可见即已记录」与事件白名单不变式。** v3 事故后彻底放弃向会话日志写自定义事件，per-session 状态迁到 dsh home sidecar；harness-roundtrip 测试以真实 `SessionStore + JsonlSessionPersistence` 冷加载回路 + `SessionFormatUnsupportedError` 陷阱守卫固化该防线。这是对框架**持久化契约**最深的适配。

**A4. 上下文贡献命名与排序遵循框架惯例。** `reference-libs:policy` 采用 `域:类型` 命名（与 `sandbox:policy` / `approval:policy` 同类），order 150 与框架「工具指导 100–199」的排序约定同带；空列表返回空串、零 token 注入，符合 systemPrompt 的「空贡献不占 token」语义。

**A5. UI 集成走官方 slot 而非自绘侵入。** dock 胶囊挂 `conversation.input.dock`、命令结果走 `conversation.chat.commandview` keyed 槽位；v7 起纯 CSS 对齐（零测量、零竞态），与官方「UI 挂载优先使用现有 slot」的开发规范一致。

**A6. 静默数据通道遵循官方先例。** `/api/ref-lib/*` 路由参照 dsh-ssh / dsh-persona-memory 的 `ctx.webServer` 自注册模式，loopback 护栏（源地址 + Host + Origin + `Sec-Fetch-Site`）镜像 dsh-ssh 的 `isLoopbackRequest`——与框架防御模式（defensive-patterns）同源。

**A7. 工程防线与框架测试文化对齐。** L0 纯函数 → L1 真实 loader 装载 → L2 harness 边界回归 → L3 隔离开发环境 → L4 实验前备份，与 DSH 对插件「不炸真实 profile」的要求一致；peerDependencies 全部对齐宿主版本族 `^0.1.1-rc.2`。

### 2.3 适配偏差与架构层面短板

**B1. 能力形态偏差：纯上下文注入，未使用工具 seam（最重要）。**
ref-lib 面向模型的能力交付方式是 `systemPrompt.context` 注入规则文本 + 让模型用通用 fs/bash 工具自行读取。对比框架原生建议「添加面向模型的能力 → 在 `ctx.tools` 上注册；其 schema 加入提示词组装」：
- 参考库查证**没有结构化工具契约**（无参数 schema、无 `output.schema` 校验、无 `finalizeContent`、无 `presentCall/presentResult` 卡片）；
- 强制执行是**提示词级软约束**（MUST/ALWAYS 措辞），而非流水线级硬约束（`tools/pre-execute` 守卫 / 单调守卫 / `ToolRestriction`）；
- 工具执行流水线的全部把关能力（超时、审批、沙箱包装、结果归一化、UI 呈现）对本插件的查证行为不可见。

**B2. 检索能力缺位：注入的是「路径清单 + 规则」，不是「检索能力」。**
参考库以「目录」为单位注册，模型需要自己决定读哪些文件、如何 grep、如何判断覆盖。没有：库内索引、关键词检索工具、相关性排序、覆盖度检查（「本次任务是否已查过参考库」）。对大型库（数千文件）而言，纯路径清单 + 模型自由读取的开销与不确定性显著。

**B3. 同步 IO 进入提示词组装热路径。**
`systemPrompt.context` 的 `text()` 是**同步回调**；ref-lib 在每次注入时对全部条目做 `statSync` 实时探测（service.list → refreshAvailability）。库多、文件系统慢（网络挂载/冷缓存）时，**每次模型请求的组装都会被同步 stat 拖慢**；512 会话内存缓存虽缓解读盘，但 stat 不可缓存。

**B4. 配置面与官方 settings seam 不对齐。**
框架限制（rc.6 起确认）：`dsh-apiproxy` 对浏览器端 settings namespace 维护**显式白名单**，第三方插件 namespace 默认不可被浏览器读写（官方标注 deferred work）。ref-lib 因此只能自建 sidecar + 自绘面板，无法进入官方「设置」页；`directory-picker` 行为只能经 `cordis.patch.yml` 手工切换。

**B5. 注入模板膨胀与多语言缺位。**
定稿英文模板约 80 行静态文本 + 逐库条目；库多时 token 线性增长，且**无截断/折叠/按需展开**策略；模板固定英文，与 client 的双语（zh/en）能力不对称（client 已全量本地化，注入规则仍是英文）。

**B6. 导入为单向快照，存在时效性风险。**
跨会话导入/继承均为 fork 时刻快照、不回流；源会话后续变更不会同步，长周期项目存在知识漂移；「同路径重复导入」需人工逐条决策，无自动合并。

**B7. 继承语义对 subagent 谱系的影响未显式管理。**
`session/created`（`{ global: true }`）对**所有**带 `parentSession` 的新会话物化继承，含子 agent 会话（fork 提供方明确设置 parentSession；spawn 的本地子会话亦记录父会话 id）。子 agent 批量创建时，每条子会话都会复制参考库列表 → **token 与 sidecar 写入放大**；子 agent 是否真的需要完整规则与清单，目前无配置开关。

**B8. 原生目录选择器体验受宿主制约。**
系统原生对话框可能卡顿、界面语言跟随 OS（README 已知限制），属于宿主能力而非插件可控面；虽有「手动输入路径」与应用内浏览器兜底，但默认体验不一致。

## 3. 插件能力可行性与落地收益研判

### 3.1 四维度可行性评估

#### 3.1.1 技术可行性 —— 高（9/10）

- **依据**：插件仅使用文档化的官方 seam（commands / systemPrompt / webServer / sessions / sessionQuery）；构建产物（tsc + tsdown → lib/）与 peerDeps 对齐宿主版本族；L0–L2 测试全绿（v13 达 195 项），harness-roundtrip 证明会话日志零污染；`scripts/dev-isolate.sh` 提供隔离真机验证路径。
- **风险点**：正确性依赖模型对提示词的服从（B1）；同步 stat 热路径（B3）；多 dsh 进程共享同一 home 时 sidecar 写并发（当前无文件锁，靠单写者假设 + 原子 rename 兜底）。

#### 3.1.2 运行稳定性 —— 高（8.5/10）

- **依据**：sidecar 原子写（tmp + rename）、畸形文件容错读（返回空列表不覆盖）、LRU 缓存（512 会话上限）、失效条目不注入、`session/created` 监听器绝不抛错（announce 契约：抛错会回滚会话挂载）、sessionQuery 缺失时逐级降级、路由 400/403/405/500 错误码完备。
- **风险点**：注入回调路径无 try/catch 的显式兜底（依赖内部容错保证「不抛错」）；同步 stat 在异常文件系统上可能放大延迟；跨进程写 sidecar 未加锁（当前为低频小文件，风险可控）。

#### 3.1.3 功能拓展性 —— 中高（7.5/10）

- **依据**：node half（服务/路由/命令）+ client half（dock/面板/浏览器/导入）分层清晰，纯函数（logic/render/commands/validate）与副作用分离，新增能力（搜索工具、TTL 探测、per-lib 开关）可低侵入加入。
- **制约**：注入模板为**固定英文常量**，新增规则段需模板版本化；无 settings namespace，插件级配置只能走 patch 或 sidecar；框架 RC 期 API 未冻结，升级需逐项核对（v11 已示范一次全量对齐）。

#### 3.1.4 场景适配性 —— 高（8.5/10）

- **强适配**：项目文档/API 规范/内部代码库查证（静态、权威、低变更多）；跨会话知识复用（fork 继承 + 跨会话导入）；只读合规场景（L1/L2 分层只读）。
- **弱适配**：高频实时数据（快照式注入无实时性保证）；超大型库（无索引、无检索）；需要结构化工具体验的复杂查证（当前为自由文本读取）。

**综合判定：插件方案落地可行性高，达到项目预设预期；但能力形态（上下文注入而非工具 seam）决定了其上界——「指引型」能力成熟，距离「流水线把关型」能力仍有架构级差距（见第 4 章）。**

### 3.2 落地收益量化分析

以下收益以「相对不装插件/纯提示词方案」为基准，证据锚定源码事实：

#### 3.2.1 研发效率提升

| 收益点 | 量化线索 | 证据 |
|---|---|---|
| 一次配置、长期生效 | 每条参考库注册后 per-session 持久化（sidecar），重启/恢复仍在；后续会话零重复配置成本 | service.ts（sidecar v3 持久化）、README §行为与配置 |
| 消除「每次会话重贴项目上下文」 | 注入机制按会话自动装配规则与库清单（`reference-libs:policy`），无需用户每次手写 | index.ts L141–150 |
| 减少幻觉驱动的返工 | 强制先查参考库 + 权威性条款（「参考库信息优先于模型记忆」），降低 API/规范类幻觉导致的迭代轮次 | render.ts REF_LIB_TEMPLATE（Authority 段） |
| fork/导入复用存量知识 | 分支会话自动继承（fork 时刻快照）、跨会话三步导入，避免在子会话中重复配置 | service.ts materializeInheritance / importEntries |

#### 3.2.2 人力成本优化

- **知识交接成本**：参考库把「项目事实」从个人记忆/聊天记录沉淀为可注入的权威源，新成员接入成本从「逐人讲解」降为「挂一个目录」；
- **上下文费用**：仅向有参考库的会话注入、空列表零 token（`renderRefLibs` 空串返回）——不会为全量会话无差别消耗模型上下文预算；
- **维护成本**：插件零配置（开箱即用），无需运维组件（无数据库、无向量索引、无后台服务），只读保证由沙箱强制（L1）而非人工纪律。

#### 3.2.3 工具能力复用

- **不引入新运行时**：读取复用宿主 fs/bash/workspace 能力，插件只做「路径注册 + 规则注入」；
- **复用官方数据面**：会话标题/工作区经 `ctx.sessionQuery` 补全（与宿主 `@session` 引用同源），跨会话导入不重复造轮子；
- **复用宿主安全面**：loopback 护栏、原子写、sidecar 固定目录，均建在宿主既有基础设施之上。

#### 3.2.4 业务场景赋能

- **研发知识库**：API 文档、架构决策（ADR）、代码规范目录一键挂载；
- **合规与审计**：只读约束分层保证（沙箱进程级强制只读 + 上下文软约束），适合「可查不可改」的审计场景；
- **多项目矩阵**：per-session 隔离 + 跨会话导入，支持按项目/按团队差异化配置知识源。

#### 3.2.5 智能化能力升级

- **RAG-lite 免向量化**：以「权威源优先 + routing metadata」实现轻量检索增强，无需索引/embedding 基建；
- **正确性提升**：冲突处理条款（「库间冲突时优先最相关库、显式报告冲突」）把多源一致性决策交给模型 + 规则约束；
- **可追溯性**：外部来源自报条款（"Not in reference library; external source used."）让答案来源可审计。

## 4. 问题研判与优化迭代方案

### 4.1 问题清单与根因定位

| # | 问题 | 严重度 | 技术根因 |
|---|---|---|---|
| P1 | 参考库优先为**提示词软约束**，模型可能跳序/漏查 | 高 | 能力形态选择：上下文注入（B1）而非 `ctx.tools` 工具注册；无 `tools/pre-execute` 守卫 |
| P2 | 无检索/索引能力，大库查证开销大、结果不可控 | 高 | 只注入路径清单（B2），未提供结构化检索工具与覆盖检查 |
| P3 | 每次注入同步 stat 全库，热路径延迟 | 中 | `text()` 同步回调契约 + 无 TTL 的实时探测（B3） |
| P4 | 注入模板膨胀、固定英文 | 中 | 静态模板常量 + 无折叠/截断/本地化（B5） |
| P5 | 无法进入官方设置页（namespace 白名单） | 中 | 框架限制（B4，deferred work）；插件只能自建 UI |
| P6 | 导入单向快照，知识漂移 | 中 | 快照语义设计（B6）；无订阅/同步模式 |
| P7 | 子 agent 谱系继承放大 token 与写盘 | 中 | `session/created` 全局钩子对所有带 parentSession 的会话物化（B7），无继承策略开关 |
| P8 | 原生目录选择器体验不一 | 低 | 宿主能力制约（B8）；默认未切换为应用内浏览器 |
| P9 | 多 dsh 进程共享 home 时 sidecar 写并发 | 低 | 单写者假设；无进程级文件锁 |
| P10 | RC 期框架 API 变动风险 | 低 | 框架开发者预览阶段，破坏性变更未冻结；v11 已示范全量对齐流程 |

### 4.2 优化调整策略（可落地、可执行）

#### 4.2.1 架构适配方向（解决 P1/P2，最高优先级）

**S1. 增加面向模型的「参考库检索」工具（context + tool 混合形态）。**
在 `ctx.tools` 注册 `reference_lookup`（或 `ref-lib/search`）工具：
- 参数 schema：`{ query: string, library?: string, maxResults?: number }`，output schema 约束返回结构（库名、文件、匹配片段）；
- 内部复用宿主 `ctx.subprocess`/`ctx.fs` 执行受限 grep/ripgrep（**不出库目录**，由工具体强制路径前缀校验 + `fs` 守卫），执行体经完整流水线把关（`timeoutMs`、`isConcurrencySafe`、`presentCall/presentResult` 卡片）；
- 在注入规则中同步声明「查证路径：优先调用 reference_lookup，再考虑直接读取」——把模型行为从「自由探索」收敛为「工具契约」；
- 附带收益：工具 schema 进入提示词组装（`ctx.systemPrompt.tools`），模型可见面更结构化，且工具执行可被钩子/策略拦截（`tools/pre-execute`）。

**S2. 引入查证覆盖度检查（agent/pre-step 或 post-execute 策略）。**
在 `agent/pre-step`（waterfall）或 `agent/turn-stopping`（serial）注入轻量策略：当任务涉及项目事实且本步骤尚未调用任何参考库工具/未读取参考库路径时，向模型注入一条「尚未查证参考库」的 steer/inject 提示（复用 `Agent.inject()` 不唤醒机制）。**这是把软约束升级为运行时强制的最短路径**，且完全在框架原生扩展点内。

#### 4.2.2 Agent 调度优化方向（解决 P7，中优先级）

**S3. 继承策略可配置化。**
在 sidecar 或 `cordis.patch.yml` 增加继承策略：`inherit`（现状）/ `inherit-lite`（仅注入规则、不复制清单）/ `none`（子会话不继承）；按 `header.origin`（fork / subagent / 普通）区分，避免子 agent 批量化时 token 与写盘放大；`materializeInheritance` 增加策略分支即可，纯函数逻辑保持可测。

**S4. Preset 感知（运行模式适配）。**
结合第 1.5 节 preset 机制：极简模式会话（仅 bash + str_replace_editor）不应携带参考库规则段——在 `reference-libs:policy` 的 `text()` 回调中读取当前 agent 的 preset/作用域（`assembleContextFor(agent)` 已携带 agent），极简模式下返回空串；同时保证 PTC 模式（Code Mode 组合调用）下检索工具可用。

#### 4.2.3 插件功能迭代方向（解决 P3/P4/P6/P8/P9）

- **S5. 探测降频**：`probeAvailability` 增加 TTL 缓存（如 ≥5s 内不重复 stat），`refreshAvailability` 仅在 TTL 过期或显式 `list()` 时探测；注入回调改用「上次探测结果 + 到期标记」，把热路径同步 IO 降为常量级。
- **S6. 模板工程化**：模板版本化 + 折叠策略（Top-N 库 + 「询问以展开更多」）；note 超长截断已有（120 字符），进一步压缩静态规则段；注入文本按 `ctx.locale` 输出 zh/en（与 client 双语对齐）。
- **S7. 导入订阅模式**：`/ref-lib import` 增加 `--watch` 或「订阅」选项（周期/事件驱动 diff 提示，经 `ctx.jobs` 后台任务），把单向快照升级为「快照 + 可选同步」。
- **S8. 目录选择器默认值**：README 已知限制的修复落地——将默认 `directory-picker` 切换为 `@deepseek-ai/dsh-host-directory-picker-browse`（应用内浏览器，zh/en 本地化、无卡顿），原生选择器降级为备用。
- **S9. sidecar 并发加固**：写入采用 O_EXCL 临时文件 + 重试/校验（或记录写者进程），并在 README 声明单进程假设；属低成本防御。

#### 4.2.4 能力增补拓展方向（中远期）

- **S10. 库级标签/优先级**：条目增加 `tag`/`priority`，注入时按优先级排序、按标签过滤，强化 routing metadata 精度。
- **S11. 全局默认库**：新增「workspace 级默认参考库」（随工作区/项目模板自动挂载），与 per-session 列表叠加，降低团队级配置成本。
- **S12. 结构化检索结果消费**：检索工具输出对齐 `SubagentResult` 风格的结构化块，便于模型多跳推理与上层工作流消费。

### 4.3 迭代升级路径（里程碑）

| 版本 | 主题 | 内容 | 验收标准 |
|---|---|---|---|
| v14 | 性能与体验 | S5 探测 TTL、S8 目录选择器默认值、S6 模板折叠（首版） | 注入回调无同步 stat 热点；选择器默认应用内浏览器 |
| v15 | 能力形态升级 | S1 检索工具、S2 查证覆盖检查、S4 preset 感知 | `reference_lookup` 工具注册且通过流水线把关；极简模式零注入 |
| v16 | 调度与同步 | S3 继承策略、S7 导入订阅 | 子 agent 继承可配置；导入支持可选同步 |
| v17 | 拓展与对齐 | S10 标签/优先级、S11 全局默认库、S12 结构化输出；跟踪官方 settings namespace 白名单开放并迁移 | 配置面进入官方设置页（若框架开放）；检索结果结构化 |

**优先级建议**：先 v14（低风险高回报，直接消除热路径与体验短板），再 v15（能力形态升级，把「软约束」变为「硬把关」——这是插件能否从「指引型」迈向「平台型」的关键一跃），v16/v17 视业务需要排期。

## 5. 总结

1. **适配度**：ref-lib 与 DSH「一切皆插件」架构高度同构——插件形态、扩展点选择、数据模型、UI 集成、测试文化五方面全部落在官方 seam 上，v3 事故修复更使其成为「会话日志安全」的模范插件。
2. **可行性**：技术/稳定/拓展/场景四维度均为高或中高，落地能力达到项目预设预期；上界受限之处在于**能力形态是上下文注入而非工具 seam**。
3. **收益**：研发效率（一次配置长期生效、减少幻觉返工）、人力成本（知识沉淀复用）、工具复用（零新运行时）、场景赋能（知识库/合规/多项目）、智能化升级（RAG-lite + 权威源优先）均有清晰量化线索。
4. **迭代方向**：以「检索工具化（S1）+ 查证强制化（S2）」为核心跃迁，辅以「探测降频（S5）+ preset 感知（S4）+ 继承策略（S3）+ 导入同步（S7）」的工程化打磨，可将插件从「规则指引型」升级为「流水线把关型」，彻底补齐当前与框架原生能力之间的最后落差。
